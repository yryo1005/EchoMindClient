# EchoMindClient Step 5: 録音ファイルの送信，Bluetooth機器の接続中の録音，ログアウト時の警告

## 1. 概要

Step 4の実機での確認で，2つの問題が指摘された．1つは，AirPodsの装着中に録音するとイヤホンから音が流れなくなることである．もう1つは，録音の声が小さく環境音の方が大きく聞こえることである．また，イヤホンの装着中は録音を止め，外すと再開する機能と，録音を任意のタイミングで送信するボタンが求められた．

これを受けて，イヤホンの接続中に録音ファイルへの書き込みを一時停止する機能を実装した．あわせて，Step 5として，Wi-Fiに接続し，かつ充電中の場合に録音ファイルを自動で送信する機能を実装した．送信した録音ファイルは，サーバーでの処理が終わった後に端末から削除する．さらに，書き込み中の録音ファイルを区切り，条件に関わらず送信する「今すぐ送信」ボタンを録音タブに追加した．

送信の処理は，模擬サーバーを相手に25項目の試験ですべて期待どおりに動作した．一方，EchoMindServerが依存するlibrosaは，最新版(1.0.0)でAACを読み込めないことが判明した．サーバーの環境によっては，送信した録音がすべて処理に失敗する．

## 2. イヤホンの接続中の一時停止

### 2.1 イヤホンから音が流れなくなる原因

Step 4の音声セッションは`.playAndRecord`カテゴリで，`.mixWithOthers`と`.defaultToSpeaker`を指定していた．このカテゴリでは，Bluetooth A2DP(AirPods等の音楽再生用の接続)を出力先とするには`.allowBluetoothA2DP`の指定が必要である．指定しない場合，AirPodsは出力先の候補にならない．その結果，録音中は出力がスピーカーに固定される．`.mixWithOthers`により他のアプリと同じ音声の経路を共有するため，他のアプリの音声もイヤホンから流れなくなっていた．

そこで，`.allowBluetoothA2DP`を追加した．Bluetoothのマイク(HFP)は引き続き許可しない．HFPを許可するとAirPodsが低音質の通話モードに切り替わるためである．A2DPを出力に，内蔵マイクを入力に用いる組み合わせは，iOS 27 SDKのヘッダの説明でも認められている．

### 2.2 一時停止の方式

イヤホンの接続は，`AVAudioSession.routeChangeNotification`を受け取るたびに出力先の種類で判定する．イヤホンとみなす種類は，有線(`headphones`)とBluetooth(`bluetoothA2DP`，`bluetoothHFP`，`bluetoothLE`)である．

一時停止の方式として，`AVAudioEngine`を止める方式と，動かしたまま書き込みだけを止める方式を比較した．iOSは，バックグラウンドで音声の入出力を行っていないアプリを一時停止する．このため，エンジンを止めると，その後にイヤホンを外しても経路の変化の通知を受け取れず，録音を再開できない．そこで，エンジンは動かしたまま，`RecordingFileWriter`への書き込みのみを止める方式とした．一時停止の時点で書き込み中の録音ファイルを区切り，再開後の最初の音声から新しいファイルを作成する．これにより，ファイルの途中に録音の空白が入らない．

この方式では，一時停止中もマイクは使用中となり，画面上部のマイクの使用中の表示は消えない．録音タブには「イヤホンの接続中のため一時停止しています．」と表示する．

## 3. 録音ファイルの送信

### 3.1 送信の流れ

`Services/UploadManager.swift`が送信を担う．自動で送信する条件は，Wi-Fi(または有線)でネットワークに接続し，かつ充電中(満充電で給電中を含む)であることとした．ネットワークは`NWPathMonitor`で，充電の状態は`UIDevice`で監視する．条件を満たした時点，録音ファイルが区切られた時点，アプリの起動時と前面に戻った時に送信を開始する．

録音ファイルは録音開始時刻の古い順に1件ずつ扱う．`POST /api/upload`で送信した後，30秒ごとに`GET /api/upload/{id}/status`で処理状況を確認する．`safe_to_delete_client_copy`が`true`になった時点で，ファイルと記録を削除してから次の録音ファイルに進む．送信時の`recorded_started_at`はUTCの`Z`表記(例: `2026-11-11T03:34:47Z`)とし，`client_file_id`には録音ファイルのIDを用いる．状況ごとの扱いを表1に示す．

表1: 送信の状況ごとの扱い

| 状況 | 扱い |
| :--- | :--- |
| `completed`，`rejected` | ファイルと記録を削除する |
| `duplicate`で`safe_to_delete_client_copy`が`true` | 処理済みのため，すぐに削除する |
| `failed` | 1分，2分，4分，8分と待ち時間を倍にして再送する．5回失敗すると自動での再送を止める |
| 処理状況の確認で404 | アップロード記録が失われたため，送り直す |
| 送信から1時間を超えて`processing` | 送り直す |
| 通信の失敗(サーバーの停止等) | 失敗の回数に数えず，5分後に再試行する |
| 認証の期限切れ(401) | 送信を止める(自動でログアウトする) |
| 送信中にユーザーが一覧から削除 | その録音ファイルを飛ばして次に進む |

EchoMindServerは，処理中のまま30分を超えた記録を`failed`として扱う．このため，表1の「1時間を超えて処理中」はサーバーの古いコード等に備えた予備の扱いである．アプリがバックグラウンドにある間は，常時録音によってアプリが動作し続けるため，送信も続く．録音を無効にしている場合に備えて，バックグラウンドに移る際に`BGProcessingTask`(ネットワークの接続と給電を条件とする)も予約する．

### 3.2 手動での送信

「今すぐ送信」は，書き込み中の録音ファイルを区切ったうえで，ネットワークに接続していれば，Wi-Fiと充電の条件に関わらずすべての録音ファイルを送信する．自動での再送を止めた録音ファイルと，再試行の待ち時間中の録音ファイルも対象とする．通信に失敗した場合は，その場で録音タブにメッセージを表示して終了する．

録音ファイルの区切りは，記録がデータベースに追加された時点で送信の対象になる．従来は，区切った録音ファイルの記録をメインスレッドへの非同期の処理で追加していた．この方式では，ボタンを押した直後の送信の対象に，区切ったファイルが含まれない場合がある．そこで，メインスレッドから区切った場合は，呼び出し元に戻る前に記録を追加するよう変更した．

### 3.3 録音タブの表示

録音タブに「送信」のセクションを追加し，Wi-Fiの接続，充電の状態，送信中かどうか，直近のエラー，「今すぐ送信」ボタンを表示する．録音ファイルの各行には，送信の状況を表示する．表示は「送信待ち」，「送信中…」，「サーバーで処理中」，「再送待ち(失敗n/5回)」，「送信を中止(5回失敗)」のいずれかである．

### 3.4 その他の変更

- 実機からLAN内のサーバーに接続するには，ローカルネットワークへのアクセスの許可が必要である．そのため，許可を求める際の説明文(`NSLocalNetworkUsageDescription`)を追加した．
- iOS 27で非推奨となった`BGTaskScheduler.submit`に代えて，`submitTaskRequest`を用いた．
- 録音ファイルの記録(`RecordingFile`)に送信の状態の項目を追加した．各項目には既定値を設定したため，Step 4で保存した録音ファイルもそのまま送信の対象となる．

## 4. 動作確認

### 4.1 ビルド

シミュレーター向けと実機(iPhone)向けのビルドが，警告なしで成功した．実機向けのビルドのInfo.plistに，ローカルネットワークの説明文とBGTaskの識別子(`com.yryo1005.EchoMindClient.upload`)が含まれることを確認した．

### 4.2 送信の処理の試験

`UploadManager`をmacOS上で実行する試験を作成し，模擬サーバーを相手に動作を確認した．macOSにないUIKitとBackgroundTasksの部分は代替の実装に置き換えた．試験に要する時間を短くするため，待ち時間は短縮した(処理状況の確認の間隔は0.2秒，送り直すまでの時間は1.5秒)．模擬サーバーは，ファイルの内容に応じて処理の結果を変える．結果を表2に示す．

表2: 送信の処理の試験結果

| 確認項目 | 結果 |
| :--- | :---: |
| 充電していない場合は自動で送信しない | 良好 |
| 充電を始めると自動で送信し，処理の完了後にファイルの実体と記録を削除する | 良好 |
| 古い順に1件ずつ送信し，前のファイルの処理の完了を待ってから次を送信する | 良好 |
| 送信の形式(`Z`表記の時刻，`.aac`，`audio/aac`，`client_file_id`) | 良好 |
| `rejected`は削除する | 良好 |
| `failed`は再送し，3回目の送信で成功する | 良好 |
| 404の場合は送り直す(送信2回) | 良好 |
| 処理が長すぎる場合は送り直す(送信2回) | 良好 |
| `duplicate`で削除してよい場合はすぐに削除する | 良好 |
| 5回失敗すると自動での再送を止め，その後は送信しない | 良好 |
| 手動での送信は，充電していなくても書き込み中のファイルを区切って送信する | 良好 |
| 手動での送信で，自動での再送を止めたファイルも再開する | 良好 |
| 通信の失敗は失敗の回数に数えず，メッセージを表示する | 良好 |
| 処理中にユーザーが削除しても異常終了しない | 良好 |

25項目すべてが期待どおりであった．試験の途中で，`URL.path()`が空白をパーセントエンコードするため，ファイルの存在の確認に失敗する不具合を発見した．保存先の「Application Support」には空白を含むため，この不具合があると，すべての録音ファイルが送信されずに削除されていた．`path(percentEncoded: false)`に修正した．また，「今すぐ送信」を押してから送信の処理が始まるまでの間に「送信中」と表示されない問題も修正した．

### 4.3 サーバーでの読み込みの確認

EchoMindServerは，アップロードされた音声を`librosa.load`で読み込む．アプリが書き込んだADTS形式のAACと，ffmpegで作成したAACを，2つのバージョンのlibrosaで読み込んだ．結果を表3に示す．

表3: librosaによるAACの読み込み結果

| ファイル | librosa 1.0.0 | librosa 0.11 |
| :--- | :---: | :---: |
| ffmpegで作成(10秒) | 読めない | 9.98秒 |
| ffmpegで作成し途中で切り詰め | 読めない | 5.31秒 |
| アプリで書き込み(1.86秒) | 読めない | 1.86秒 |
| アプリで書き込み(1.34秒) | 読めない | 1.34秒 |

librosa 0.11は，libsndfileで読めない形式をaudioread(ffmpeg)で読み込むため，AACを処理できる．librosa 1.0.0ではこの代替の手段が削除され，AACは「Format not recognised」となる．これは`.aac`に限らず，m4aでも同様である．EchoMindServerの`requirements_ml.txt`はlibrosaのバージョンを指定していない．このため，新しく環境を構築すると1.0.0が入り，送信した録音はすべて`failed`となる．

### 4.4 実機での確認

確認の時点でiPhoneがMacから切断されていたため，実機での動作は未確認である．

## 5. 声が小さく環境音が大きく聞こえる件

iPhoneの内蔵マイクは全方向の音を拾う．マイクの近くで生じる音(衣服との擦れ，机の振動，ポケットや鞄の中の雑音)は，離れた話者の声より大きく録音される．録音は音量を正規化していないため，再生すると全体に小さく聞こえる．マイクの故障である可能性は低いと考えられる．ただし，ケースや手でマイクの穴を塞いでいないかは確認する必要がある．

文字起こしの精度を左右するのは，音量よりも声と雑音の比である．ソフトウェアで音量を上げても，雑音も同じだけ大きくなるため，この比は改善しない．音声セッションの音声処理(`setVoiceProcessingEnabled`)を有効にすると，雑音の抑制と自動の音量調整が働く．しかし，この処理は端末の持ち主の近くの声に合わせて調整されている．そのため，会話の相手の声まで抑制し，話者分離の精度を下げるおそれがある．以上から，現時点ではアプリ側の録音方法は変更しない．実際の録音をサーバーで処理し，文字起こしの結果を見て対処を判断する．対処が必要な場合は，サーバー側で音量の正規化や雑音の除去を行う方が，元の音声を保ったまま調整できる．

## 6. ユーザーの判断を受けた変更

### 6.1 Bluetooth機器の接続中も録音を続ける

2章の方式では，Bluetoothのスピーカーや車載機器もA2DPで接続されるため，イヤホンとして扱われ，録音が一時停止する．ユーザーに確認したところ，iPhone本体のマイクで録音できる限りは，AirPodsを含むBluetooth機器の接続中も録音を続けるよう指示があった．

そこで，一時停止の判定を「出力先にイヤホンが含まれるか」から「入力がiPhone本体のマイクか」に変更した．音声セッションの有効化と経路の変化のたびに，`setPreferredInput`で入力を本体のマイクに固定する．Bluetoothのマイク(HFP)は許可していないため，AirPodsの接続中も入力は本体のマイクのままである．有線のヘッドセットを接続した場合も，本体のマイクに戻す．本体のマイクに戻せない間のみ，書き込みを一時停止する．本体以外のマイクの音声は，録音の距離や音質の条件が異なるためである．

### 6.2 ログアウトの前の警告

ログアウトして別のアカウントでログインすると，前のアカウントで録音したファイルが新しいアカウントに送信される．ユーザーの指示により，ログアウトの前に警告を表示して，アカウント間で録音が混ざらないようにした．

警告を表示する条件は，端末に未送信の録音ファイルがある場合と，常時録音が有効な場合である．常時録音が有効な間は録音中の内容があり，ログアウトの後に送信されるため後者も含めた．警告では次の3つから選ぶ．

- 「録音を停止してすべて送信」: 常時録音を停止し，録音中の内容を区切ってすべて送信する．送信が終わった後に改めてログアウトする．
- 「録音を削除してログアウト」: 常時録音を停止し，未送信の録音を送信せずに削除してからログアウトする．
- 「キャンセル」．

設定画面のアカウントの欄には，未送信の録音の件数も表示する．

### 6.3 実機への導入

変更後のアプリを実機向けにビルドし，iPhone 16 Pro Maxにインストールして起動した．`RecordingFile`に送信の状態の項目を追加した後も，Step 4で保存したデータを持つアプリが異常終了せずに起動し続けることを確認した．

### 6.4 実機での確認結果

ユーザーが実機で6.1，6.2の変更と送信の機能を確認し，いずれも問題がなかった．実サーバーに送信した録音が処理され，分割された発言の音声の再生と質問への回答まで，一連の流れが動作した．文字起こしの精度と音声の分割の精度には課題があるが，これはサーバー側の処理の課題である．

## 7. 未解決の論点・次に検討すべき事項

- EchoMindServerの環境のlibrosaのバージョンを確認する必要がある．1.0以降の場合は，`librosa<1`に固定するか，ffmpegで16kHzモノラルに変換してから読み込むようサーバー側を修正する必要がある．
- 実機で確認する必要がある項目は次のとおりである．
  - AirPodsの装着中に他のアプリの音声がイヤホンから流れること．
  - AirPods等のBluetooth機器の接続中も録音が続き，録音タブが「録音中」のままであること．
  - 未送信の録音がある状態でログアウトすると警告が表示されること．
  - 「今すぐ送信」で送信され，サーバーでの処理の完了後に一覧から消えること．
  - Wi-Fiに接続し，かつ充電中の場合に自動で送信されること．
- 実機からの接続には，サーバーURLにMacのIPアドレス(確認時点では`10.30.105.27`)を指定し，サーバーを`--host 0.0.0.0`で最新のコードにより起動する必要がある．
- ログイン期限切れ(401)による自動でのログアウトでは警告を表示できないため，未送信の録音が端末に残る．次に別のアカウントでログインすると，そのアカウントに送信される．録音ファイルに録音したアカウントを記録するかを検討する必要がある．
- 実際の録音をサーバーで処理し，文字起こしの精度を確認する必要がある．声が小さいことへの対処は，その結果を見て判断する．
- 次の作業はStep 6(状態表示・設定画面の拡充)である．
